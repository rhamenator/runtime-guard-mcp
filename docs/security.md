# Security model

The server is advisory. A model may ignore a result and use another tool. For hard containment, configure the agent host to make this server the route for relevant operations and apply OS sandbox or policy controls.

The path tool checks a proposed path after `Path.resolve`; it rejects traversal beyond configured roots and sensitive names. It cannot prevent time-of-check/time-of-use races or detect all sensitive filenames. Do not treat its verdict as a capability token.

The command tool never executes. Pattern and `shlex` checks can miss shell language constructs, aliases, environment expansions, and platform-specific syntax. Unknown and compound commands require review. Any `SAFE` result means only that the current heuristics found no listed risk.

Budget counts are caller-reported. The server cannot independently know model token usage or actions made outside it. Each caller's metric history is capped at 8192 reservation records per metric, and fingerprint history is capped at 4096 records process-wide. A reservation that would exceed either state cap returns `BLOCKED` without partially consuming another metric; records are released when their sliding windows expire. High-frequency legitimate callers can hit these state caps before the numeric budget. In memory windows reset on restart, and multiple replicas do not share limits. The optional SQLite database stores only redacted decision metadata in a SHA-256 hash chain. The server verifies the chain on startup and refuses a tampered database; it checks the latest row before each append. If an audit write or this check fails, the tool returns `BLOCKED` / `AUDIT_UNAVAILABLE` without its computed result. Policy state may already have changed before that audit failure, so retry only after repair. `AuditLog.verify_integrity()` detects altered and deleted interior rows; a process-local tip hash detects tail deletion or replacement before the next append while that process remains alive. Tip comparison and insertion share an immediate SQLite transaction. Use one writer process per audit database; another writer changing the tip causes fail-closed behavior. After restart, tail deletion still requires an external anchor to detect. A full interior check is not performed on every append. Startup migration and integrity checks retain one audit row at a time in Python rather than materializing the whole table. Integrity verification holds the process writer lock for its full scan, so long scans delay new audit writes. Scan time remains proportional to record count; native SQLite cache/RSS and database/WAL growth are not capped by this change. Configure filesystem permissions and retention externally.

Masking is best effort. It recognizes several credential forms, email addresses, and US Social Security number shapes, but cannot identify every secret or private identifier. Raw secrets are not logged or persisted; the in-memory lookup stores hashes to keep placeholders stable. The process allows at most 128 unfinished streams and 4096 distinct secret mappings per caller; exceeding either limit returns a `BLOCKED` result with no text. A stream blocked while masking must be ended with `final=true` before its identifier can be reused; the blocked stream is discarded without emitting its tail. Buffered raw stream tails are removed when a stream finishes, and clients should always finish abandoned streams. These bounds may deny further masking until streams finish or the process restarts. The process memory can still contain transient sensitive data, so run it under the user's account and restrict access.

HTTP defaults to loopback. Exposing it beyond loopback requires a bearer token and TLS proxy. The HTTP server rejects duplicate Host, Origin, Authorization, Content-Length, and Content-Type headers, malformed Host or Origin authorities, unsupported transfer encoding, and non-JSON POST media types before dispatch. Origins must use HTTP or HTTPS. It does not interpret chunked request bodies. The server limits active handlers to 32 and returns 503 when all slots are occupied. It closes sockets after five seconds of inactivity or five seconds total per connection, including incomplete headers or bodies. The absolute deadline prevents a peer from holding a handler indefinitely by slowly dripping bytes, but can disconnect legitimate slow uploads. These are process-level resource bounds, not caller quotas; a client can still consume all slots for short intervals, and the listen backlog and upstream proxy need their own limits. For production, add per-client identity, stronger HTTP transport compatibility checks, and a sandbox around any future active executor.

Both stdio and HTTP decode requests as UTF-8 JSON. Duplicate object keys, non-finite constants or overflowed floating-point numbers, invalid UTF-8, nesting deeper than 64 levels, and more than 8192 structural markers (`[`, `{`, `:`, or `,`) outside strings return a JSON-RPC `-32700` parse error before dispatch. The scan ignores markers inside quoted strings and runs before the JSON decoder constructs containers. This avoids ambiguous parsing and limits container amplification from both deep and wide payloads. The one-megabyte frame cap still permits large strings and many primitive bytes, so this is not a complete memory-use limit. A malformed frame does not poison the next request.

Stdio reads at most 1 MiB plus one byte before deciding whether a line is oversized, then drains the rest in 64 KiB pieces and returns one controlled error. It does not parse the remainder as additional requests. The client still controls how fast it writes; host-level process limits remain useful for a compromised local client.

HTTP parser and unsupported-method errors use generic JSON status descriptions rather than the standard handler diagnostics, which can echo request lines or methods. Error responses close the connection, and HEAD responses omit the body. These transport errors are HTTP errors rather than JSON-RPC envelopes.

Configuration files use the strict bounded request JSON parser before validation. Duplicate keys cannot silently replace earlier operator settings. Invalid, unreadable, or oversized files stop startup before serving; the error does not echo file contents.

Audit hash backfilling applies only to legacy tables lacking both hash columns. A partially present hash schema or a cleared hash in an existing chained audit fails startup instead of being repaired. This does not detect an attacker who replaces the entire database with a plausible legacy store; filesystem access controls and an external anchor remain necessary.

Bearer-token validation compares UTF-8 encoded values with the standard library constant-time comparison helper. Missing, near-match, wrong-length, wrong-scheme, and non-ASCII incorrect values return generic 401 responses. This reduces content-dependent comparison timing; it is not a network timing-resistance certification and does not hide token length.

## Audit storage failure and recovery

SQLite lock attempts use a 250 ms busy timeout rather than the default five seconds. A contending writer causes an audited tool to return `BLOCKED` / `AUDIT_UNAVAILABLE` without its computed result. This bounds SQLite lock waiting per attempt; it does not bound total request time, Python lock contention, scanning, filesystem I/O or CPU. Releasing the external transaction permits the next append without restarting the server. Keep one server writer per audit file.

Regression tests use real SQLite `SQLITE_FULL` errors by limiting the temporary database page count, and restore that capacity to verify recovery and chain integrity. This is a bounded backend-capacity fixture, not a host filesystem-full simulation or a production disk cap. A loopback API probe holds a separate `BEGIN IMMEDIATE` transaction, verifies fail-closed/no appended row plus responsive ping, releases it and verifies a new audited decision. The probe also runs against installed wheels in CI. Budget/masker state may already have changed before audit failure; no rollback of that policy state is promised. Disk/WAL growth, retention, actual filesystem-full and sustained resource tests remain open.

## Audit record-count policy

With audit enabled, the default `audit_max_records` limit is 100,000 committed records; operators may configure another positive integer. The append lock guards the count check and commit, and the count is rebuilt by startup integrity verification. Capacity exhaustion returns `BLOCKED` / `AUDIT_CAPACITY`, retains existing records and appends nothing. Restart, concurrent calls, or lowering the limit below an existing file's count do not clear that count. Failed database writes do not increment it. No deletion, truncation, automatic rotation or silent replacement is performed.

This bounds new server-generated records per configured file, not filesystem bytes, WAL/cache growth, scan time, pre-existing oversized records or external database writers. Capacity rejections have no audit row because storage is full by policy. Caller-reported budgets and masking state may already have changed. External monitoring and deliberate archival are required to avoid an availability outage. Audit remains optional when `audit_db` is null.

The tested manual workflow stops the writer, preserves an SQLite backup, and starts a fresh configured file. Keep the old verified chain and final hash in trusted external storage. New chains have no automatic link to old files; detecting omitted or replaced archives and signing cross-file manifests remain release-review concerns. Preserve filesystem controls and one writer per database. This record-count policy does not close actual filesystem-full, sustained resource or cross-file provenance gates.

## Atomic audit startup

Schema creation, legacy hash-column/backfill migration, and verification share an immediate SQLite transaction. Commit occurs only after verification succeeds. Startup failure closes the connection, rolling back pending schema/backfill updates and releasing its locks. WAL journal-mode setup is performed before the transaction and is not reverted. Verification still takes time proportional to the file size and holds a database write lock throughout initialization; this does not make concurrent server writers supported.

Expected workspace/storage/integrity errors terminate the CLI before it starts either transport, with status 2 and a generic setup diagnostic. Raw SQLite/trigger errors, file paths and tracebacks are not printed for these handled failures. Tests use a real aborting SQLite trigger on the second legacy row to prove that neither added columns nor partially backfilled rows survive a failed startup. Removing that fixture trigger permits retry/migration. Installed probes also exercise corrupt files, directory paths and a contending write transaction. This is orderly-failure evidence, not a power-loss, forced-kill or actual filesystem-full simulation. Human repair must preserve original evidence and verify integrity rather than erase it.
